## 三、覆盖口径

卡片不得再显示含义模糊的“覆盖 11/11”，必须同时显示：

- 省级地区覆盖：成功地区数 / 31；
- 分析区覆盖：至少一个代表点成功的分析区数 / 33；
- 代表点覆盖：成功点数 / 75；
- 明日预测覆盖与今日对比基线覆盖必须分开显示；
- 完整覆盖、部分覆盖、完全缺失的分析区数量；
- 只有一个点可用的分析区数量，首屏不得把“33/33 有数据”误写成“33/33 完整”；
- 数据源、实际生成时间和“今日+明日”范围。

多代表点分析区只有部分点成功时必须标为“部分覆盖”，不能伪装成完整覆盖。

## 四、风险、稳定和缺失必须守恒

所有配置分析区必须互斥进入以下分类：

- Top 5 风险；
- Top 5 之外的较低优先级风险；
- 稳定分析区；
- 数据完全缺失分析区。

必须满足：

```text
Top 5 展示数 + 其余风险数 + 稳定数 + 完全缺失数 = 配置分析区总数
成功代表点数 + 缺失代表点数 = 配置代表点总数
```

展示规则：

1. Top 5 之外的风险不能静默丢失，必须显示“另有 X 个较低优先级风险分析区未在卡片展开”。
2. 风险第 6 名以后不得计入稳定分析区。
3. `stable_count == 0` 时不得出现“稳定市场 0 个，已折叠”。
4. `stable_count > 0` 时显示“稳定分析区 X 个，精简卡未逐一列出”。
5. 缺失数据不得算作稳定。
6. “已折叠”不得冒充可交互组件。
7. 多代表点的风险必须保留各自城市和时间窗；不得把 A 点的时间窗与 B 点的负荷、光伏或风信号拼成同一事件。
   同一个代表点存在多种信号时也必须分别计算时窗，`direction / window / driver / change` 必须来自同一个结构化信号事件。
8. 只有 1 个点可用时必须显示“1/N 点，不可外推全区”，且不得进入分析区资源排行。
9. 资源排行只使用对应角色内至少 2 个可用代表点的等权样本；没有真实业务权重时不得宣称加权聚合。

## 五、展开全部分析区

- 支持“展开全部分析区”“查看全部分析区”，并兼容“展开全部市场”“晨报全部详情”等旧表达。

- 展开版必须列出所有已覆盖分析区，稳定分析区不能只列名称而没有明细。

- 当前会话没有有效晨报快照时，提示用户先生成晨报，不能继承其他用户、群或线程的快照。
- 顶层生成卡片后，用户回复机器人卡片形成的新线程也必须能展开；需按机器人回复消息 ID 保存同用户上下文别名。
- 09:00 定时群发成功后，必须按 `chat_id + 卡片 message_id` 保存只读共享线程指针；群内任一用户回复该定时卡可展开，但其他群或其他线程不得继承。

## 六、跨进程持久缓存

- 定时任务和手动请求共享数据卷中的独立 SQLite 缓存。
- 缓存键至少包含报告日期、市场配置版本和报告版本。
- 保存 `generated_at`、`expires_at`、结构化覆盖率、分类统计、精简卡片和完整卡片。
- 使用事务和生成租约实现 single-flight；并发请求只能发生一轮全国抓取。
- 缓存读取必须校验 schema、报告版本、配置版本、覆盖率、统计和两张卡片；可解析但字段残缺的 JSON 也必须视为 miss。
- 缓存必须跨服务重启可用；默认保留 24 小时以支持当天晚些时候展开，跨日或配置版本变化时重新生成。
- 零覆盖或生成失败不得覆盖最近一次有效快照。
- 协程取消或进程退出时必须立即释放生成租约，不能让其他请求空等 600 秒。
- 时间口径固定为 Asia/Shanghai，不能依赖容器 UTC 的 `date.today()`。

## 七、发送安全与定时任务

- 晨报分析、缓存和卡片构建不得带固定群发送副作用。
- 手动生成只回复当前飞书事件所在会话。
- 定时入口显式区分：
  - `precompute`：只计算和写缓存，绝不发送；
  - `send`：读取新鲜缓存后向已配置固定群发送。
- `DRY_RUN=1` 下所有飞书发送方法调用次数必须为 0。
- 推荐北京时间 08:50 预计算、09:00 发送。
- 飞书 event_id 的 processing 租期必须覆盖全国生成的最长 600 秒窗口，避免同一事件重投后重复回复。
